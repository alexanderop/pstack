What are Cursor and Codex?

Both help you work on software using an AI assistant. You can describe a change in ordinary language, let the assistant examine your project, and review what it produces. The details of the app and its available tools determine what it can actually do.

For this article, picture a project folder containing a small online shop. You ask: “The shopping cart shows the wrong total. Find out why.” An assistant might read the cart code, run a test, edit a file, and test the result.

You will encounter different ways to use these products: a desktop app, an editor integration, a terminal program, or a cloud service. A terminal is where you run text commands. Local means on your computer; cloud means on a remote computer. A feature available in one of these environments may be absent in another.

Our question is specific: what did the authors change to make the Cursor version of pstack work in their chosen Codex environment? This article does not rank the two products.

The pieces you will see throughout the article

Model — the system producing the answers
The model interprets your request and decides what to say or do next. Its name and reasoning settings are configuration choices. Changing the model does not automatically add access to your browser or files.
Agent — the assistant doing a task
An agent uses a model together with instructions and tools. A tool is an action it can request, such as reading a file or running a command. Think of an agent as the active worker.
Skill — a reusable set of task instructions
A skill might explain how to investigate a bug: reproduce it, find the cause, fix it, and check the result. It can also contain scripts and examples. Reading a skill gives an existing agent a method to follow.
Rule — a standing instruction
For example: “Use TypeScript in this project.” A rule gives ongoing guidance; a skill explains a particular workflow. A workflow is simply an ordered way of doing a task.
Subagent — an additional worker
The main agent can hand a bounded job to another agent: “Review the cart calculation and report mistakes.” The main agent then uses the returned findings. Loading a skill and starting a subagent are separate actions.
Plugin — a package you install
A plugin bundles reusable capabilities so you can install them together. pstack is such a package. Its instructions tell the assistant how to work; the application still supplies the actual tools and permissions.

How to read the rest: each section introduces the idea, shows what this project changed, and explains why you would notice it. Configuration examples are reference material; you do not need to memorize the file names.

01 / The core idea

pstack gives the assistant a repeatable way to work.

pstack is a collection of instructions for doing engineering work: investigate before changing code, compare designs, delegate focused tasks, review the result, and prove it works. Its main entry point, poteto-mode, chooses a playbook for your request. A playbook is a checklist for a kind of work, such as fixing a bug or reviewing a change. “Poteto” is the project’s name for its preferred working style; it is not a separate AI model.

Those ideas travel well. But instructions such as “start a background agent on this model” rely on specific tools supplied by the host application. That surrounding machinery is often called the agent harness. Here, it means the application’s tools for running commands, starting workers, and managing their work. A port is an adaptation that makes a project work in another environment.

The repository accounts for all 158 upstream files, with 47 skills and 23 playbooks. “Accounted for” means retained, adapted, or explicitly replaced. It does not mean every behavior works identically.

Read this as a case study. These are the choices this port made for the host interfaces it targeted. They are not a timeless feature matrix for every Cursor or Codex product.
02 / Remembering instructions

How does the assistant know to keep using pstack?

Suppose you carefully explain how you want bugs fixed. You do not want to repeat that explanation in every message. Skills and project instructions let you save it.

A skill is usually stored in a file called SKILL.md. Markdown (.md) is plain text with simple formatting. To invoke a skill means to explicitly ask the assistant to use it.

Some of the port was changing where the application looks for things. A plugin manifest is the file describing the package and where its contents are. The Cursor plugin manifest became a Codex plugin manifest. The invocation example changed too: /poteto-mode became $poteto-mode.

$poteto-mode Find why the cart total is wrong.
First show the bug, then fix it and check the result.

The spelling above is the convention used by this port. The current official docs describe skill selection differently across OpenAI interfaces, so use the skill picker your app provides.

Cursor · settings attached to the skill
disable-model-invocation: true
mode: true
reminder: New task? Apply mode.

Cursor-specific fields controlled explicit invocation and reminded the agent about the mode.

Codex · agents/openai.yaml
policy:
  allow_implicit_invocation: false

The port preserves explicit invocation through Codex skill metadata. Keeping the workflow active needs a separate instruction.

These settings are for the plugin author. The Cursor excerpt is shortened. “Implicit invocation” means the assistant chooses the skill itself; “false” turns that off in this port’s metadata.

For one task, you can say: “Use poteto-mode throughout this task.” For future tasks in a repository, the port provides an optional AGENTS.md instruction directing Codex to load the workflow.

AGENTS.md is a text file of instructions for work in a project folder. For example, it can say “Use the installed pstack workflow for engineering tasks.” Codex reads applicable project instructions before working. Cursor also supports AGENTS.md; this file is not exclusive to Codex. OpenAI documentation · Cursor documentation.

What changes for you? Installing the plugin does not turn on a permanent mode. The skill supplies the method; your task instruction or repository instructions determine when to apply it.
03 / Agents and isolation

Three assistants need clear jobs and places to work.

Imagine one assistant fixing the cart, another checking discount rules, and a third reviewing the result. The extra assistants are subagents. The main assistant gives them jobs and collects their findings. In the code and docs, “spawn” simply means “start another agent.”

The Cursor source uses Task with fields such as subagent_type and run_in_background. The port rewrites delegation around Codex’s spawn, message, follow-up, and wait tools. A review panel is several agents reviewing the same work. If the application permits only a few agents at once, the port starts some now and the rest when slots become free.

A repository is a project tracked with Git, the version-control tool. A branch keeps a line of changes separate. A checkout is the actual set of project files in a working folder. Switching branches inside one folder does not give every agent its own folder.

There are two separate responsibilities: give each worker a job, and give each writer a place to work. This port explicitly creates separate working folders for concurrent writers instead of assuming its Codex spawn tool will do that automatically.

All three workers can edit the same file in the same checkout. Their edits may overlap. Spawning agents alone has not separated their work.

A worktree is another working directory attached to the same Git repository, usually on its own branch. Separate branches still need integration and review.

Cursor’s current docs describe subagent environments using worktrees or cloud machines. This article’s Codex comparison concerns the port’s delegation contract, not a claim that Codex has no worktree support. Cursor subagent environments.

A named worker needs a job description

A persona is a written role, such as “be a careful reviewer.” It is not another model. Think of the difference between hiring a person and giving that person a job description.

The bundled agents/poteto-agent.md describes how an agent should behave. Its presence alone does not register a selectable Codex agent. This port offers optional TOML agent definitions (small configuration files that register a named role); otherwise, it starts a generic agent and tells it to read the persona file.

Likewise, “review only; do not write” is an instruction. A sandbox is a technical restriction on what an agent can do. A read-only filesystem sandbox can prevent file changes even if the agent attempts them. The port explicitly warns against confusing the two.

04 / Choosing models

Which AI should do each job?

A role is the job, such as “reviewer.” A model is the AI chosen for it. Reasoning effort is a setting controlling how much reasoning work a supporting model is asked to do. More effort can take more time and resources; it is not a promise that the answer will be correct.

pstack assigns different models to different jobs: quick edits, exploration, difficult design, and independent review. Cursor’s source stored overrides in an always-applied rule. The port stores preferences in a file that its delegation workflows explicitly read.

Cursor
~/.cursor/rules/
  pstack-models.mdc

alwaysApply: true

Model slug includes effort
Codex
~/.codex/pstack-models.md

gpt-6-astra @ high

model: gpt-6-astra
reasoning_effort: high

Schematic comparison, not a file to paste as-is. The Codex preference is split into separate model and effort fields. A “model slug” is just the exact identifier the tool expects. The ~ in a path means your home folder.

The port validates available models against the active host. An auto or inherit-parent preference means “do not choose a different model and effort for this worker.” The application can then use inherited settings. The model names in the example are this repository’s configured choices, not a recommendation for what you must select.

A real tradeoff: the source’s default panels mixed Claude, Grok, and GPT. This port’s defaults use several GPT models. You still get multiple attempts and reviewers, but less provider diversity. That is a choice in this port’s defaults.
05 / Background work

“Wake when something happens” became “check what changed.”

A subagent works on a delegated task now. An automation starts work when a trigger says it is time. The trigger could be a clock (“every morning”) or an event (“a new bug report arrived”). These solve different problems.

Benny is pstack’s automation pack for Slack issue reports. To triage means to inspect and classify a report: is it a bug, what is affected, and what should happen next? One workflow triages a report; another reproduces a confirmed bug and may prepare a fix. The Cursor integration used event triggers. The Codex adapter uses scheduled polling. Polling means checking repeatedly: “Have any new reports arrived?” A webhook is a message one service sends to another when an event occurs.

Example: with an illustrative five-minute polling interval, a report posted at 10:01 might be discovered at 10:05. An event-driven service is notified when the report arrives, although execution can still be delayed. Five minutes is an example, not this plugin’s fixed schedule.

A ledger is a saved record of progress. Here it remembers reports already seen, actions already taken, and unfinished work. “Durable” means it survives the current process stopping.

This required actual state-management code. A report might have been seen already, might still be waiting for a verdict, or might have created a tracker issue just before a run crashed.

  1. Discover without skipping.Read paginated history and record unseen reports using their exact IDs.
  2. Remember unfinished work.Keep pending reports even after the discovery cursor moves forward.
  3. Recover without blindly repeating writes.If an issue creation had an uncertain result, read back and reconcile before trying again.

Long-running agent orchestration follows the same principle: save a durable ledger, inspect the real branch and PR state after a restart, then recreate workers. Old agent IDs are not permanent worker handles.

Current docs add an important boundary: OpenAI documents supported app-event triggers for eligible ChatGPT web/mobile plans, while local desktop work has different scheduling requirements. This pstack port uses its polling adapter; that does not mean every OpenAI interface lacks events. Local scheduled work needs the computer on and the app running. What about a button that starts an AI task?

A backend is the program behind a page that performs its work. A bridge is a small program connecting two systems. In this case, clicking a web-page button sends a request to a local program, which starts Codex.

The source’s make-bot-ui could create a Cursor webhook routine. The port adds a localhost HTTP service that invokes codex exec. codex exec is a terminal command for running a Codex task without an interactive chat. “Localhost” means the service is reachable on this computer. Its bundled demo supports only summarize and dry-run (validate the request without starting Codex), with validation, limits, and timeouts. Other operations need an adapted, reviewed workflow.

What changes for you? Installing the plugin does not start a bot, connect Slack, or keep a task alive overnight. Those behaviors need a configured host, integrations, durable state, and an available scheduler.
06 / Tools and memory

Replace the assumptions about where things live.

Instructions can only use tools that actually exist in the application. A paragraph saying “open Slack” cannot create a Slack connection.

MCP stands for Model Context Protocol. It is a standard way to expose external tools and data to an AI application. In practical terms, a connected service might let the assistant search issues or read a Slack thread. It still needs to be installed or connected and have the right access.

A transcript is a record of a previous conversation. A runtime contract is this port’s written agreement about tools, paths, and behavior. Here are the remaining changes:

UI verification uses the tools the host exposes

The source referenced Cursor companion skills such as control-ui and control-cli. The port routes to available browser, computer-use, terminal, or project verification tools. “Prove it in the real interface” remains the requirement.

Skill authoring and cleanup lose Cursor-specific dependencies

Cursor’s create-skill becomes Codex’s skill-creator. The external deslop dependency becomes an explicit diff-cleanup pass for narrating comments, dead code, unnecessary guards, and unrelated changes.

Recall must understand Codex session records

Cursor stored transcripts in workspace-specific directories. Codex session files live under ~/.codex/sessions/YYYY/MM/DD/. The port first matches the workspace against session_meta.payload.cwd, then reads the relevant session events.

Paths and integrations must be resolved explicitly

The port adds a shared CODEX.md runtime contract. Skills resolve bundled files from their installed skill location, rather than assuming the target repository is the plugin directory. Available apps and MCP tools are discovered at runtime; the plugin does not bundle a missing service.

07 / Put it together

Imagine asking: “Fix this cart bug and have two agents review it.”

Suppose the shop shows €20 for two €10 items, then incorrectly shows €10 after you add a third. You want the assistant to find the cause, fix it, and get two other agents to review the fix.

Here is the sequence in ordinary language. The port supplies the Codex-specific instructions needed to carry it out:

  1. Load the method.Use pstack’s bug-fix checklist. Add the items in the app and observe the incorrect total before editing code.
  2. Choose the worker.Choose an available model for the fix and give the worker its job description: investigate the cause, make a focused change, and explain the evidence.
  3. Arrange the workspace.If multiple agents will edit code, give them separate working folders and clear responsibilities. Two agents only reading the code do not need separate copies just to avoid edits.
  4. Review within host capacity.Give the reviewers the exact changes. One might check calculation edge cases; another might inspect the tests. Ask them to report findings without changing files.
  5. Verify and integrate.Check that three €10 items now total €30. Also check removing an item and applying a discount. Read the reviewers’ findings and resolve real problems.
  6. Save a handoff if the task must resume.If work stops, save what changed and what is still unfinished. Later work must check the current files rather than assume the old workers are still running.

The engineering method tells the agent what good work requires. The runtime adapter tells it how to perform that work here.

08 / Evidence and limits

How do we know the replacement really works?

There are different levels of checking. A file check can show that a skill exists. A local test can show that the ledger remembers a report. An end-to-end test must show that a real report arrives, triggers the intended work, and produces the expected result.

The repository’s integration report records installation checks, persona loading, browser interaction, a local HTTP-to-Codex request, worktree isolation, and local state-recovery tests. It also records a scheduler configuration test that created, inspected, and deleted a paused automation.

A saved schedule does not prove a future wakeup. The report leaves timed delivery, live Slack/tracker triage, real PR merging, and arbitrary application reproduction dependent on tests in the target environment.

Your first experiment

Start with one small, visible task.

You do not need an overnight automation or a fleet of agents to understand pstack. Once the plugin is installed, start with a question about your own project:

Use the installed pstack workflow to explain
how the shopping-cart total is calculated.
Do not change any files.
Explain the result in plain language.

Then try a small fix and ask for one separate reviewer. You can observe the difference between a skill (the instructions being followed), a subagent (the extra reviewer), and a tool (the action used to read or test your code).

A pull request, or PR, is a proposal to merge code changes for review. CI means automated checks run by a service. Those become relevant when you start using pstack’s review and shipping workflows; you do not need them for the first read-only experiment.

Check your understanding

Does a skill start another agent? Not by itself. It gives instructions; those instructions may ask the main agent to delegate.

Does a separate agent mean separate files? Not necessarily. The workspace arrangement determines that.

Does installing the plugin start Benny? No. The connections, schedule, and state storage need setup.

Does AGENTS.md belong only to Codex? No. Both products document support for it.
